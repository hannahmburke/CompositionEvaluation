## Experiment generation

Due to the lack of an existing benchmark dataset for this problem, we adapted the data set used in reference [3] in the manuscript. This contains processes originally extracted from the SAP R/3 collection. We adapted these processes to create data-aware service compositions by converting each of the three processes into a composition of between 3 and 5 services. As such, they include a range of different processes at the service level (including atomic, linear, XOR split and nested XOR splits), as well as the composition level (including linear and XOR split). 

For each of the 3 compositions, there are 6 fully-compliant experiments in the dataset. 
Each experiment contains 12 numeric variables, and a different set of write operations that test the scalability by varying the number of variable updates (1, 2, and 3 times, as indicated by W in the experiment name) and in the domain size of the non-deterministic write operations (3 and 10, as indicated by U in the experiment name). 

We evaluated and compared the privacy-preserving approach proposed in this paper with the original process-transparent approach. To specify a finite input domain for each of the 12 numeric variables, we chose ranges broad enough to capture all of the possible values that occur from the write operations. This depends on the size of non-determinism in the write operations, and whether that variable undergoes \emph{addition}, \emph{subtraction} or \emph{both} across all its write operations. For the non-determinism size of 3, this was [0,9] for \emph{addition} variables, [-9,0] for \emph{subtraction} variables and [-3,3] for \emph{both}. For the non-determinism size of 3, this was [0,30] for \emph{addition} variables, [-30,0] for \emph{subtraction} variables and [-10,10] for \emph{both}. 

## Evaluation Input

Each directory under `compositions/` corresponds to a composed service system used in the evaluation and contains:

- `composition_model.pnml` - the overall composition model.
- `composition_image.png` - a visualisation of the composition.
- Experimental instances derived from the benchmark dataset described in reference [3] in the manuscript. These affect the write operations of the activities within the internal services. 
    - `U_<n>` - domain size of possible variable updates within activities
    - `W_<m>` - overall number of variable updates within the composition

For each service (`service-A`, `service-B`, etc.), the experimental input consists of:

- `*-model.pnml` - the service process model.
- `*-annotations.xml` - write operations of activities within the service
- `*-image.png` - a visualisation of the service model.

## Intermediate Output: Certificates

The `certificates/` directory contains the certificates generated by our approach for individual services.

A certificate is a symbolic summary of a service with respect to a particular obligation. It contains:

- the obligation definition being analysed;
- the symbolic constraints representing input conditions under which the service is compliant with respect to the obligation;
- the input/output map, containing
  - symbolic constraints partitioning the possible execution outcomes;
  - the resulting obligation state and status for each outcome; and
  - symbolic expressions describing how service execution may modify process variables.

Each certificate is generated from the `*-model.pnml` and `*-annotations.xml` files of an individual service. Compliance verification at the composition level is then performed using the collection of service certificates together with the `composition_model.pnml` file. The certificates are propagated through the composition model, allowing the compliance status of the overall system to be determined without requiring access to the internal process models or annotations of the constituent services.

## Experimental Results

`composition_results.csv` contains the results for all experimental configurations evaluated in the paper, including certificate generation, certificate propagation, and overall time to execute the privacy-preserving compliance verification procedure. This is compared to the white-box approach where the composition-level verification has full transparency of the internal service details.
